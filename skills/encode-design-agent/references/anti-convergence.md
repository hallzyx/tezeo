# Anti-convergence: how to keep two projects from looking alike

Convergence comes from defaults: the same "safe" typefaces, the same rounded-card-plus-gradient grammar, the same brand references in the brief. Counter it with procedure, not taste.

## 1. Font procedure (fonts are derived, never defaulted)

1. Write the **voice** in three words from `CONTEXT.md` (e.g. "calm, exact, human" or "loud, athletic, playful").
2. Translate voice into **type traits**: contrast (low/high), width (narrow/wide), x-height, terminals (soft/sharp), stroke modulation, personality (geometric / humanist / grotesque / slab / serif / display).
3. Shortlist **3-5 free families per role** (display, body, mono-if-needed) that match those traits. Browse the catalogue instead of recalling favourites.
4. **Over-used defaults are guilty until proven innocent.** If a candidate is one of: Inter, Roboto, Open Sans, Poppins, Montserrat, Space Grotesk, DM Sans, Plus Jakarta Sans, Manrope, Outfit, Sora, Bricolage Grotesque, Instrument Sans, JetBrains Mono, IBM Plex Mono, Fraunces: it needs a written reason tied to the voice, and it must beat one non-default alternative in a side-by-side render. (The list is a smell test, not a ban.)
5. Render the same headline, a paragraph and a number set in the finalists on the real background. Choose by looking.
6. Record in `DECISIONS.md`: chosen, runner-up, why, and which trait of the product it serves.
7. **Never carry a font pairing over from a previous project** unless the new product shares its voice for a stated reason.

## 2. Motif procedure (shapes and patterns come from the domain)

- A motif must be traceable to something in the domain world or the name: an object, material, process or ritual. Write the trace: "motif X because the product does Y".
- Prefer a *system* (a repeatable construction rule) over a decoration: how it scales, tiles, animates, shrinks to a favicon.
- Avoid motifs that are fashionable rather than meaningful: blurry gradient blobs, glassmorphism everywhere, generic abstract waves, three-circle logos, mascots with no story.
- Vary the **layout grammar** too: not every product is "centred card on a soft background". Consider density, grid, asymmetry, edge treatment, how sections are separated, how emphasis is made (size, weight, colour, space, rule).

## 3. Palette procedure

- Start from the domain's real colours and the emotional target, not from a favourite hue.
- Assign each colour a **job** (brand, surface, accent, status). Status colours must stay unmistakable and outside the accent range.
- Verify contrast numerically, and compute colour distance between status colours and any user-customizable accent.
- Different products should differ in **temperature, saturation and the neutral family** (warm/cool/tinted greys), not just in the hex of the primary.

## 4. The swap test (run before choosing a direction and before hand-off)

1. Cover the logo and the product name on a screenshot. Could it plausibly belong to the other projects the user has made, or to a famous product? If yes, it is not distinctive enough.
2. Swap the product: would this exact look fit an unrelated product (a bank, a snow-gear shop, a children's app) without a single change? If yes, it is generic; find the domain-specific idea that would break that fit.
3. Name three choices (type, shape, colour or motion) that exist only because of this product. If you cannot, go back to Phase 2.

## 5. Briefing the designer without leaking a style

- Do not name reference brands as style anchors ("make it like X"). Name *qualities* instead ("warm, precise, quietly confident").
- Do not paste hex, fonts or motifs from earlier projects into the brief. Pass the Context Pack, not the old look.
- Ask for three directions before one design.
